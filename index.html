01

What is Docker

The same code can work on one machine and fail on another. Docker exists so that the environment travels with the code.

Key ideas

  • An app depends on more than its source: runtime, libraries, OS packages, config and a start command.
  • An image packages all of that, except the kernel.
  • A container is a running (or stopped) instance of an image.
  • Docker builds, ships and runs images. It is not a virtual machine.

The problem: "it works on my machine"

Source code is only part of a program. When the code runs, it also depends on its environment:

  • the language runtime (Python 3.12 or 3.8?)
  • library versions from requirements.txt
  • OS packages and native libraries, such as the MySQL client libraries
  • configuration and environment variables
  • the exact command that starts the app

Send someone app.py and requirements.txt and none of that comes along. Their machine fills the gaps with whatever it happens to have installed.

Shipping source code is not the same as shipping a runnable application.

Packaging the environment

Docker's answer is to package the app together with everything it needs to run:

Package = application + runtime + libraries + OS user-space

One thing is deliberately left out: the kernel. Containers use the kernel of whatever machine they run on. The package carries the user-space files (the bits that make a system look like Debian or Alpine) but not the core of the operating system.

Why a ZIP of the repo isn't enough

A ZIP is just the source tree. It doesn't pin the Python version, bring the native libraries, install OS packages or say how to start the app. An image does all four, in a standard format every Docker host understands.

Image vs container

Image

The packaged template. You build it once, it never changes, and you can copy it to any machine.

Container

A running or stopped instance of an image. One image can start many containers.

Docker is often compared to a shipping container. The useful part of the analogy is standardisation: one box shape that every crane, ship and truck can handle. It says nothing about how Docker isolates processes.

What Docker is

Docker is a platform to build, ship and run applications in containers.

PieceWhat it does
Docker EngineThe background service (daemon) that builds images and runs containers.
Docker CLIThe docker command you type. It only sends requests to the Engine.
ImageImmutable, reusable template.
ContainerAn instance of an image.
RegistryStores and distributes images. Docker Hub is the public default.
Docker DesktopThe app that installs all of the above. On Windows and macOS it also runs the Linux VM that Linux containers need.

How the pieces talk Added

The docker command is only a client. It sends each request to the Docker daemon, dockerd, which does the real work and owns your images, containers, networks and volumes.

What Docker is not

Docker is not a virtual machine, a programming language, a cloud provider, Kubernetes, or an automatic security solution. Each of those solves a different problem.

Why use it

  • Consistent environments. The same image runs on your laptop, in CI and on the server.
  • Less overhead. No guest OS per app, so many more apps fit on one machine than with a VM each.
  • Fast startup. Starting a container starts a process, not an operating system.
  • A standard artifact. CI systems and cloud platforms all know how to build, store and run images.

Limits

  • It doesn't fix bad application code.
  • It doesn't replace pip or npm; it packages their result.
  • Linux containers still need a Linux kernel somewhere.
  • Isolation is not the same thing as security.

Common mix-ups

✗"Docker is a VM."No. Containers share the host kernel instead of booting their own.
✗"An image is a full operating system."It has user-space files and dependencies, but no kernel.
✗"Docker runs anywhere."The host still needs a compatible kernel family and CPU architecture. An ARM-only image won't run on an x86 server without emulation.
✗"Docker replaces pip or npm."Those still install dependencies. Docker packages the result together with the environment.

Test yourself

Why can identical source code behave differently on two machines?

Because the environment differs: runtime version, library versions, OS packages, configuration, and the start command all come from the machine, not the source.

What does an image contain, and what does it leave out?

It contains the app, its runtime, libraries and OS user-space files, plus metadata such as the default command. It leaves out the kernel, which comes from the host.

Image vs container, one line each.

Image: the immutable packaged template. Container: a running or stopped instance created from it.

Which part of Docker actually builds images and runs containers?

The Docker Engine (the dockerd daemon). The docker CLI only sends it requests.

What do you push to and pull from a registry?

Images. Containers are created locally from those images.

02

Docker vs virtual machines

A VM pretends to be a whole computer. A container is an ordinary process that has been given its own private view of the system.

Key ideas

  • A VM virtualises hardware and boots its own guest kernel.
  • A container is an isolated process running on the host's kernel.
  • Namespaces limit what a container can see; cgroups limit what it can use.
  • On Windows and macOS, Docker Desktop runs Linux containers inside a Linux VM.

The actual difference

The biggest difference is what gets virtualised. A VM gets virtual hardware and runs a complete operating system on it, kernel included. A container gets an isolated view of the system but uses the host kernel; there is no second kernel inside it.

That one difference explains the practical trade-offs:

  • containers usually start in seconds; a VM has to boot an OS first
  • containers use less disk and RAM, so more of them fit on one host
  • VMs isolate more strongly, because they don't share a kernel
  • a VM can run a different OS from the host (a Windows guest on a Linux host); a container can't

Inside a container: namespaces and cgroups

A container is a normal Linux process started from an image, wrapped in two kernel features:

The container's filesystem is the image's files plus a writable layer on top. It can look like a small Debian or Alpine system because it contains their user-space, but there is still no guest kernel.

Isolated per container

  • process tree
  • files
  • network view
  • hostname
  • resource limits

Still shared

  • the kernel
  • the physical hardware

Privileged mode and some host mounts weaken the boundary further.

Container isolation is stronger than two ordinary processes, and weaker than two VMs.

Side by side

They work together

VMs and containers are not either/or. A typical production setup is a cloud VM running a container runtime that runs several containers. The VM gives the machine-level boundary; the containers make it cheap to run many apps inside it.

Your own laptop is the other everyday example. Linux containers need a Linux kernel, and Windows and macOS don't have one, so Docker Desktop quietly runs a small Linux VM and puts the Engine and your containers inside it.

Which one when?

Reach for a VM when you need

  • a different OS or kernel
  • stronger isolation between tenants
  • to move or reproduce a whole machine
  • a separate OS because policy requires it

Reach for a container when you need

  • the same app environment on laptop, CI and server
  • many services on one host
  • environments you can create and throw away in seconds

One question settles most cases: do I need another computer (with its own kernel), or just another environment for a process? The first is a VM, the second a container.

Common mix-ups

✗"A container is a lightweight VM."It has no guest kernel and no virtual hardware. It is a process with a private view.
✗"Containers have no OS."Misleading. They can contain a full Linux user-space like Debian or Alpine. What they lack is a separate kernel.
✗"Containers are more secure than VMs."Not automatically. The kernel is shared, so the boundary is thinner.
✗"Using Docker means I'm not using a VM."On Windows and macOS, Docker Desktop runs your Linux containers inside a Linux VM.

Test yourself

What does a VM have that a container doesn't?

Its own guest kernel and virtual hardware. A container uses the host kernel directly.

Namespaces vs cgroups?

Namespaces control what a process can see (PIDs, network, filesystem, hostname). Cgroups control how much it can use (CPU, memory, process count).

Why do containers start so much faster than VMs?

Starting a container starts a process. Starting a VM boots an entire operating system first.

On Windows, where do your Linux containers actually run?

Inside a Linux VM (WSL 2) that Docker Desktop manages, on that VM's Linux kernel.

You need to run a Windows-only app on a Linux server. Container or VM?

A VM. A container can't bring a different kernel; a VM can boot a Windows guest.

03

Images & containers

An image is the template. A container is one instance of it, with a thin writable layer of its own.

Key ideas

  • One image, many containers. Changes inside a container never flow back into the image.
  • An image is a stack of read-only layers, shared on disk between images and containers.
  • Each container adds its own writable layer; removing the container deletes it.
  • Stopped is not deleted. A stopped container keeps its files until you remove it.

Template vs instance

ImageContainer
What it isImmutable template: a filesystem plus start-up metadataAn instance created from an image
Does it run?Never. It's data, not a process.Running or stopped
Can it change?No. You build a new image instead.Yes, in its private writable layer
How many?One templateZero, one or many per image
What you shipThisYou run these; you don't ship them

Two analogies that are good enough: class vs object in programming, or recipe vs one prepared dish in cooking.

Inside an image: layers

An image isn't one big blob. It is a stack of layers, each a set of filesystem changes on top of the one below: base OS user-space, then the runtime, then your dependencies, then your code. Layers are read-only and identified by content, so identical layers are stored once and shared.

Names and tags

Images are referred to as name:tag, for example python:3.12 or myapp:1.0. The tag is a human-friendly label that can be moved to a different image later. The image's real identity is its content hash (an ID like sha256:3f1c…). If you leave the tag off, Docker assumes :latest, which is just a default label, not a promise of "newest".

Inside a container: the writable layer

When Docker creates a container from an image, it:

  1. reuses the image's read-only layers (no copy);
  2. adds a new, empty writable layer on top;
  3. applies isolation: namespaces and cgroups;
  4. starts the container's process, when asked to.

Every file the container creates or changes lands in its writable layer. If it edits a file that came from the image, Docker first copies that file up into the writable layer and edits the copy (copy-on-write). The image underneath never changes.

Stopped container ≠ deleted container.

When the main process exits, the container moves to stopped but still exists, writable layer and all. Starting it again brings its files back. Removing it deletes the writable layer for good, and a new container from the same image starts with a clean one. That's why the writable layer counts as ephemeral: data you care about belongs somewhere else (see Storage).

The lifecycle

Try the lifecycle

Run the commands and watch what happens to the container and its writable layer. The image never changes.

Where images come from

Build

You write a Dockerfile and run docker build. The result lands in your local image cache.

Pull

You download an existing image from a registry with docker pull, or Docker pulls it for you when docker run or FROM needs it and it isn't cached.

docker images lists the local cache. Anything already there doesn't need downloading again. To share an image you docker push it to a registry; again, you move images, not containers.

Common mix-ups

✗"The image is the running app."The running thing is a container. An image never runs.
✗"I installed a package in the container, so the image has it now."It only went into that container's writable layer. Add it to the Dockerfile and rebuild.
✗"Stopped means deleted."A stopped container still exists, with its files, until you docker rm it. docker ps -a shows it.
✗"Ten containers means ten copies of the image."They share the image's read-only layers. Each adds only a thin writable layer.
✗"Use docker commit to save a container as an image."It works, but it isn't how images should be made. Change the Dockerfile and rebuild, so the steps are repeatable.

Test yourself

You created a file in container A. Can container B (same image) see it?

No. The file is in A's private writable layer. B has its own, and the image is untouched.

A container exited. Are its files gone?

No. Stopped is not deleted. docker start brings it back with the same files. Only docker rm deletes the writable layer.

Why can many containers from one image be cheap on disk?

They share the image's read-only layers. Each container only adds its own thin writable layer.

What is copy-on-write?

When a container changes a file that came from the image, Docker copies it into the container's writable layer and changes the copy. The image layer stays read-only.

What does python:3.12 mean?

The image named python with the tag 3.12. The tag is a label; the image's real identity is its content hash.

04

Writing a Dockerfile

A Dockerfile is the recipe. docker build follows it step by step and produces an image.

Key ideas

  • Four instructions get you started: FROM, COPY, RUN, CMD, plus WORKDIR.
  • RUN happens while building. CMD only runs when a container starts.
  • COPY freezes files into the image. Editing them on your laptop needs a rebuild.
  • Docker reuses unchanged steps, so copy requirements.txt before the rest of the code.

Four steps for a Python app

  1. FROM: take a Python base image
  2. COPY: put my code in the image
  3. RUN: install the libraries
  4. CMD: say how to start the app

WORKDIR isn't one of the four, but set it anyway so copying, installing and running all happen in a known folder (usually /app) instead of /.

FROM python:3.13
build time

Start from an existing image: Debian user-space plus Python. Docker uses your local copy or pulls it from Docker Hub; you never write docker pull in a Dockerfile.

Pin a tag like 3.13 rather than latest. -slim variants are smaller. Still no kernel inside.

WORKDIR /app
build time

Create /app and make it the current folder for every step after this one.

COPY . .
build time

COPY <from build context> <into image>. Here: everything in the folder you passed to docker build goes into /app. It's a snapshot, not a live link to your laptop.

RUN pip install --no-cache-dir -r requirements.txt
build time

Runs during the build, using the pip inside the image, not the one on your machine. The installed packages become a layer.

--no-cache-dir keeps pip's download cache out of that layer, so the image stays smaller.

CMD ["python", "app.py"]
run time

Not run during the build. It's saved as metadata: the default process when a container starts.

Prefer this exec form (a JSON list) over CMD python app.py. Only the last CMD counts, and docker run myapp <command> overrides it.

Build it, run it

docker build -t myapp .
docker run --rm myapp
  • -t myapp names (tags) the image.
  • . is the build context: the folder whose files COPY can see. Docker also looks there for a file called Dockerfile.
  • --rm deletes the container automatically when its process exits.

Keep junk out: .dockerignore

The whole build context is sent to the Docker daemon before the build starts. A .dockerignore file (same idea as .gitignore) keeps things out that the image doesn't need, and stops secrets sneaking in through COPY . ..

.dockerignore
.git
.venv
__pycache__/
*.pyc
.env

Layer order and the build cache

Every instruction is a step, and if a step's inputs haven't changed since the last build, Docker reuses its result from cache. But once one step changes, every step after it runs again.

With COPY . . before RUN pip install, any code edit changes the copy step, so pip reinstalls everything even though requirements.txt didn't change. Try both orders:

Which steps rebuild?

Since the last build I changed

Naive: copy everything, then install

  1. FROM python:3.13
  2. WORKDIR /app
  3. COPY . .
  4. RUN pip install -r requirements.txt
  5. CMD ["python", "app.py"]

Better: copy requirements first

  1. FROM python:3.13
  2. WORKDIR /app
  3. COPY requirements.txt .
  4. RUN pip install -r requirements.txt
  5. COPY . .
  6. CMD ["python", "app.py"]

Dockerfile, cache-friendly order
FROM python:3.13
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]

Dependencies change rarely, so the install layer stays cached. Code changes often, and now only the final COPY reruns. Projects 03 and 04 in this repo already use this order; project 02 uses the naive one.

Other instructions you'll meet Added

InstructionWhat it does
ENV KEY=valueSets an environment variable for later build steps and for the running container. Project 03's MySQL Dockerfile uses it for the root password and database name.
ARG NAME=defaultA variable that exists only during the build. Set it with docker build --build-arg NAME=value.
EXPOSE 5000Documents which port the app listens on. It does not publish anything (see Port mapping).
ENTRYPOINT ["python"]Fixes the executable. With an ENTRYPOINT, CMD becomes its default arguments, and anything after the image name in docker run replaces those arguments instead of the whole command.
USER appuserRuns later steps and the container's process as that user instead of root. A cheap safety win for real images.

Mental model

FROMstart from someone else's imagebuild
COPYput my files into the imagebuild
RUNrun a command that changes the image's filesystembuild
CMDthe default process for containersrun

The Dockerfile is the recipe. The image is the cooked dish, packed to go. A container is one serving.

Common mix-ups

✗"FROM installs Python on my laptop."It picks the base of the image. Nothing changes on your machine.
✗"COPY keeps the files in sync."COPY is a one-time snapshot at build time. For live files, use a bind mount (see Storage).
✗"RUN pip install installs packages on the host."It only changes the image being built.
✗"CMD runs during docker build."Nothing starts until docker run. CMD is just recorded.

Test yourself

RUN vs CMD?

RUN executes while the image is being built and saves the result as a layer. CMD is the default command executed when a container starts.

You edited app.py, but the container still runs the old code. Why?

COPY froze the old file into the image. Rebuild the image and start a new container from it (or use a bind mount while developing).

Why copy requirements.txt before the rest of the code?

So the slow pip install layer depends only on requirements.txt. Code edits then only rerun the final COPY, and the install comes from cache.

What does the trailing . in docker build -t myapp . mean?

The build context: the current folder. COPY can only see files inside it, and Docker looks for the Dockerfile there by default.

A Dockerfile has two CMD lines. Which one runs?

Only the last one. And a command given to docker run replaces it for that container.

05

Port mapping

A container has its own network. Port mapping opens a door from a port on your laptop to a port inside the container.

Key ideas

  • -p HOST:CONTAINER. The left number is where you connect; the right is where the app listens.
  • The two numbers don't have to match: -p 8080:5000 is normal.
  • EXPOSE documents a port. It doesn't publish anything.
  • Inside a container the app must listen on 0.0.0.0, not 127.0.0.1.

The problem

In projects/02_flask_app, Flask listens on 0.0.0.0:5000 inside the container. That's port 5000 in the container's own network, not on your laptop, so http://localhost:5000 in your browser fails until you publish the port.

Left side = host port. Right side = container port.

docker run --rm -p 8080:5000 myapp
# now open http://localhost:8080

The -p syntax

The full form is [host_ip:]host_port:container_port[/protocol].

FlagMeaning
-p 8080:5000Host 8080 → container 5000, TCP, on all host interfaces
-p 5000:5000Same number on both sides
-p 127.0.0.1:8080:5000Only your own machine can connect, not other devices on your network
-p 8080:5000/udpUDP instead of TCP
-p 5000Container 5000 → a random free host port
-PPublish every EXPOSEd port to random host ports. Explicit -p is easier while learning.

To see what actually got published, check the PORTS column of docker ps. 0.0.0.0:8080->5000/tcp reads as "host 8080 to container 5000".

Will the browser reach Flask?

Change one setting at a time and follow the request hop by hop.

EXPOSE is not port mapping

EXPOSE 5000 in a Dockerfile is documentation, plus a hint for -P. It never opens a port on the host.

EXPOSE-p / Compose ports:
WhenImage metadata, at buildContainer run time
Reachable from the host?NoYes
Needed for -p to work?NoYes, if the host needs access

You can run -p 8080:5000 on an image with no EXPOSE at all. The only requirement is that the process really listens on 5000.

Why the app must listen on 0.0.0.0

Inside a container, 127.0.0.1 is the container's own loopback, not your laptop's. Published traffic arrives on the container's network interface, eth0. An app bound only to loopback never hears it.

app.py (project 02)
if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000, debug=True)

Host ports can't be shared

Publishing is for the host only

Publish a port when something outside Docker needs in: your browser, Postman, a database GUI on your laptop. Containers talking to each other don't need -p at all; they use a Docker network (next chapter).

Be careful with databases. Publishing to all interfaces can make them reachable from your whole network. For local-only access, bind to loopback:

docker run -d -p 127.0.0.1:5432:5432 postgres:16

Compose uses the same HOST:CONTAINER pairs:

ports:
  - "8080:5000"
  - "127.0.0.1:5432:5432"

Host port = where you connect. Container port = where the app listens.

Common mix-ups

✗"EXPOSE publishes the port."It only documents it. Use -p or Compose ports:.
✗"-p 8080:5000 makes the app listen on 8080."The app still listens on 5000. Docker forwards 8080 to it.
✗"localhost in the container is my laptop."It's the container itself.
✗"Two containers can't both use port 5000."They can inside. They just can't publish the same host port on the same interface.

Test yourself

In -p 3307:3306, which number does your laptop use?

3307, the left one. 3306 is the port inside the container.

Your Dockerfile has EXPOSE 5000 but the browser can't connect. Why?

EXPOSE doesn't publish. Run the container with -p 5000:5000 (or any HOST:5000).

You mapped the port correctly and it still fails. What's the classic cause?

The app is listening on 127.0.0.1 inside the container. Make it listen on 0.0.0.0.

How do you publish a database only to your own machine?

Bind to loopback: -p 127.0.0.1:5432:5432.

06

Networks

Being on the same machine doesn't let containers talk to each other. Being on the same Docker network does, and by name.

Key ideas

  • Every container has its own network namespace: its own IP and its own localhost.
  • Containers on the same network can reach each other. Separate networks are isolated.
  • On a user-defined network, container names work as hostnames.
  • Between containers, use the container port. -p is only for the host.

Two different paths

From your laptop

browser → localhost:8080 → -p → app:5000

Needs a published port.

Between containers

app → db:5432

Needs a shared Docker network. No -p.

Container-to-container traffic should never go out to the host and back in through a published port. It goes over a Docker network.

What a Docker network is

Think of it as a virtual switch that containers plug into. Containers on the same switch can reach each other; a container on a different switch can't, unless you plug it into both. docker network ls shows the three that always exist: bridge, host and none.

DriverWhat it means
bridgeA private virtual network on one host, with NAT to reach the outside. The default, and the one you'll use.
hostThe container uses the host's network stack directly. No isolation, and no -p: the app binds host ports itself.
noneNo network at all, only loopback.
overlayOne network spanning several machines (Docker Swarm). Skip until you have more than one host.

Linux also has macvlan and ipvlan, where a container looks like its own machine on the physical network. Not needed while learning.

The default bridge vs a network you create

A plain docker run without --network lands on the default network, bridge. It works for one-off containers, but it has no name lookup.

Default bridgeUser-defined bridge
Reach others by IPYesYes
Reach others by nameNoYes, built-in DNS
IsolationShared with every container that didn't pick a networkOnly what you attach
Use it forQuick one-off experimentsAnything with two or more containers
 
docker network create mynet
docker run -d --name db  --network mynet postgres:16
docker run -d --name app --network mynet -p 8080:5000 myapp
# inside app, postgres://db:5432 just works

On the default bridge you'd need raw IPs (which change when containers are recreated) or the legacy --link flag. Create a network instead.

Compose does it for you

Docker Compose creates one user-defined network per project and attaches every service to it. The service name becomes the hostname, so app reaches the database as db:5432 without you running docker network create.

services:
  app:
    build: .
    ports:
      - "8080:5000"
  db:
    image: postgres:16
    # no ports: reachable as db:5432 from app, not from the laptop

Two Compose projects get two separate networks. A service in one can't see a service in the other unless you add a shared external network.

Name, port and -p

  • Hostname: the container or service name, on a user-defined network.
  • Port: the port the process listens on inside its container, like 5432 or 3306.
  • -p: an extra door for the host. Other containers don't use it.

A classic wrong turn. MySQL is published as 3307:3306, so Flask tries localhost:3307. Inside the Flask container, localhost is Flask itself, and nothing is listening there. Use the name and the container port: mysql_container:3306.

Isolating parts of an app

Networks double as walls. Attach each container only to the networks it needs:

docker network connect backend-net api   # plug a running container into another network
docker network inspect mynet             # who is attached, with which IPs

Internet access: containers on a normal bridge can make outgoing connections (through NAT). Incoming connections from outside still need a published port.

Mental model

networkwho can talk to whom
nameDNS hostname on a user-defined network
container portwhere the process listens
-pan extra door from the host

Put related containers on one user-defined network, talk by name and container port, and publish only what the host needs.

Common mix-ups

✗"Same machine means same network."The default is isolation. Each container has its own localhost.
✗"Container names always work as hostnames."Only on user-defined networks, which include Compose's. Not on the default bridge.
✗"--network host is faster Docker."It removes network isolation entirely. Only use it when you mean to.
✗"No ports: in Compose means no networking."Other services on the project network can still connect. ports: is only about the host.

Test yourself

Why can't app resolve db on the default bridge?

The default bridge has no built-in DNS for container names. Create a network (or use Compose) and both join it.

MySQL runs with -p 3307:3306. Which address should a Flask container use?

mysql_container:3306, the container name and the container port, over a shared network. 3307 is only for tools on the host.

How do you stop the web tier from reaching the database?

Put them on different networks and attach only the API container to both.

Which command adds a running container to another network?

docker network connect <network> <container>

07

Docker Compose

Instead of remembering a chain of docker commands, describe the whole stack in one YAML file and start it with one command.

Key ideas

  • A Compose file lists services. docker compose up builds or pulls images, creates a network and starts everything.
  • Each service name is a hostname on the project network.
  • image: uses an existing image; build: builds one from a local Dockerfile.
  • depends_on only orders start-up. Add a health check when you need "ready".

The problem

Two containers already means two long docker run lines, each with an image, a name, a network, environment variables, ports and a restart policy. Forget --network once and Flask can no longer resolve mysql_container.

What Compose does

Compose reads a file called compose.yaml (or the older docker-compose.yml) and:

  1. builds or pulls the images,
  2. creates a project network (a user-defined bridge),
  3. creates and starts a container for each service,
  4. attaches them all to that network.

It isn't a new kind of container. Same Engine, same images, same networking; the file just records how the pieces run together.

docker compose, with a space, is the current command, built into Docker. docker-compose with a hyphen is the old standalone tool.

The top-level version: line is obsolete. Modern Compose ignores it (and warns about it), so you can delete it.

The project's Compose file, line by line

This is projects/04_docker_compose: the same Flask + MySQL app as project 03, but with no MySQL Dockerfile and no hand-typed commands.

services:
  mysql_container:

Each key under services: is a service. That key is also the hostname other services use, which is why app.py connects to host='mysql_container'.

    image: mysql:8.0

Use the official image as-is, pulled from Docker Hub. No Dockerfile.

    container_name: mysql_container
    restart: always

container_name is optional and only pins the name you see in docker ps (default: project-service-1). restart: always restarts the container whenever it stops.

    command: --default-authentication-plugin=mysql_native_password

Extra arguments for mysqld, switching it to the older password method. This option exists only up to MySQL 8.0; it was removed in 8.4, one more reason to pin the tag.

    environment:
      MYSQL_ROOT_PASSWORD: demopassword
      MYSQL_DATABASE: demodb

Environment variables the MySQL image reads on first start: set the root password and create demodb. These replace the ENV lines from project 03's Dockerfile.

    ports:
      - "3307:3306"

For tools on the host only. Flask still talks to 3306 over the network.

    healthcheck:
      test: ["CMD", "mysqladmin", "ping", ...]
      interval: 10s
      timeout: 5s
      retries: 5

Every 10 seconds, ask MySQL whether it's up. Once a check passes the service is healthy; five failures in a row and it's unhealthy.

    volumes:
      - ./MySQL/init.sql:/docker-entrypoint-initdb.d/init.sql

A bind mount of one file into the image's init folder. The first time MySQL starts with an empty data directory, it runs the scripts in that folder, which creates the users table.

  flask_container:
    build: Flask/.

Build an image from the Dockerfile in that folder, then run it. Your own app always needs a Dockerfile, because only you know how to package it.

    depends_on:
      mysql_container:
        condition: service_healthy
    ports:
      - "5000:5000"

Don't start Flask until MySQL's health check passes. Then publish 5000 so the browser can reach Flask.

The file in the repo has one portability problem: it says ./MySQL and Flask/, but the folders are named mysql and flask. That works on Windows, whose filesystem ignores case, and fails on Linux. See fixes for the repo.

image: vs build:

image: mysql:8.0

Use an existing image. Compose never looks for a Dockerfile for this service.

Official images are designed to be configured at run time, with environment:, command: and mounts.

build: ./flask

Use that folder as the build context, run the equivalent of docker build, then use the result.

Mixing both in one file is normal, and is the point of project 04.

Project 03 needed a mysql/Dockerfile just to set two environment variables and copy init.sql. Compose does both in YAML, so that Dockerfile disappears.

The project network

Compose creates a network called <project>_default and attaches every service. You never run docker network create. Services reach each other by service name and container port:

Start order and health checks

depends_on: [mysql_container] on its own only waits for the MySQL container to start, not for MySQL to be ready. A fresh MySQL takes a while to initialise, so Flask can start, try to connect, and crash.

services:
  mysql_container:
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      retries: 5
  flask_container:
    depends_on:
      mysql_container:
        condition: service_healthy

Commands

Run these from the folder that contains the Compose file.

CommandWhat it does
docker compose upCreate the network, build or pull images, start every service, and stream the logs in your terminal
docker compose up -d --buildSame, in the background (detached), rebuilding build: services first
docker compose psList this project's containers
docker compose logs -f flask_containerFollow one service's logs
docker compose downStop and remove the containers and the network. Images stay, and so do named volumes unless you add -v.

Mental model

Compose filethe recipe for the whole stack
serviceone role in the app (web, db) and how to get its image
service namehostname on the project network
image: / build:pull an existing image / build from a local Dockerfile
docker compose upnetwork + every container, in order

One file. One network. Talk by service name and container port.

Common mix-ups

✗"Compose is like Kubernetes."Compose runs one project on one machine using the normal Docker Engine. Kubernetes runs workloads across a cluster of machines.
✗"image: builds the Dockerfile in that folder."It never builds. That's what build: is for.
✗"depends_on means the database is ready."Only with a health check and condition: service_healthy.
✗"Publishing 3307:3306 means Flask should use 3307."Flask is on the network and uses 3306. 3307 is for the host.
✗"Other services find a container by its container_name."They use the service key. container_name only changes what docker ps shows, and stops you scaling that service.

Test yourself

Why can Flask connect to host='mysql_container'?

Because mysql_container is the service key, and Compose's project network resolves service names as hostnames.

Why does project 04 need no MySQL Dockerfile?

It uses image: mysql:8.0 and configures it at run time with environment:, command: and a bind mount for init.sql.

What does docker compose down remove, and what does it keep?

Removes the containers and the project network. Keeps images and named volumes (unless you add -v).

Flask crashes on start-up because MySQL isn't ready. Fix?

Add a healthcheck to MySQL and depends_on: … condition: service_healthy to Flask, or make the app retry its connection.

08

Storage

A container's writable layer dies with the container. Anything you want to keep has to live somewhere else: in a mount.

Key ideas

  • Removing a container deletes its writable layer and everything written there.
  • A bind mount connects a host file or folder you choose. Good for code, config and init scripts.
  • A named volume is storage Docker manages. Good for database files.
  • compose down keeps named volumes. compose down -v deletes them.

The problem

MySQL keeps its data in /var/lib/mysql. Without a mount, that folder lives in the container's writable layer, so docker rm or docker compose down takes the whole database with it. The same goes for anything written under /app that wasn't part of the image.

If data must outlive the container, store it outside the writable layer.

Two kinds of mount

Both make some storage appear at a path inside the container; the app just sees a normal file or folder. The difference is who controls the source side.

Bind mountNamed volume
SourceA host path you pick: ./mysql/init.sql, ./flaskA name Docker manages: mysql_data
Who manages the filesYou, as normal files and foldersDocker, inside its own data directory
Typical useSource code, config, init scriptsDatabase files, uploads, anything that must outlive the container
Host path in the YAML?YesNo, only the name

Telling them apart

-v, --mount and Compose volumes: all express the same idea. The short form is -v source:target:

Source looks like a path: bind mount

./mysql/init.sql:/docker-entrypoint-initdb.d/init.sql

Source is a plain name: named volume

mysql_data:/var/lib/mysql

Bind mounts

You point at a file or folder that already exists on the host, and the container reads and writes those exact bytes. Edit on the host and the process sees it; write in the container and the host file changes.

Project 04 already uses one, for MySQL's first-run script:

volumes:
  - ./MySQL/init.sql:/docker-entrypoint-initdb.d/init.sql

That isn't the database. It's one SQL file placed where the MySQL image looks for setup scripts on its very first start.

Live code while developing

volumes:
  - ./flask:/app

The image still contains a COPY of the code, but the bind mount covers /app with your real folder. Edit, refresh, no rebuild.

Trade-offs. The host path must exist; if it doesn't, Docker may create a folder where you meant a file. On Docker Desktop, binds go through the Linux VM, which is fine for development. On Linux, file ownership (UID/GID) inside the container may not match yours.

Named volumes

You choose only a name and a path in the container. Docker creates and stores the volume.

services:
  mysql_container:
    image: mysql:8.0
    volumes:
      - mysql_data:/var/lib/mysql   # the actual database lives here

volumes:
  mysql_data:                       # declare the name at the top level
docker run -d -v mysql_data:/var/lib/mysql mysql:8.0   # created if missing
docker volume ls
docker volume inspect mysql_data

On Docker Desktop the real files sit inside the Linux VM, not in a folder next to your repo.

Init scripts run once. When an empty named volume is first mounted, Docker can seed it with whatever the image has at that path. After MySQL has initialised the volume, its contents win. Editing init.sql later does not re-run it while mysql_data already holds a database.

What survives compose down

ContainersNetworkImagesNamed volumes
docker compose downremovedremovedkeptkept
docker compose down -vremovedremovedkeptremoved: data gone

That one flag is the difference between "stop the stack" and "wipe the database". Use -v on purpose.

Both in one service

services:
  mysql_container:
    image: mysql:8.0
    volumes:
      - ./mysql/init.sql:/docker-entrypoint-initdb.d/init.sql  # bind: the recipe
      - mysql_data:/var/lib/mysql                              # named: the data

volumes:
  mysql_data:

Bind mount: files you edit and commit to git. Named volume: files the service generates that must survive down.

Anonymous volumes

-v /var/lib/mysql with no source still creates a volume, but with a random ID. They're easy to lose track of and pile up in docker volume ls. Give volumes names.

Mental model

writable layerscratch space; keep nothing you need here
bind mountmy host file or folder, connected live
named volumeDocker-owned storage that survives compose down

Ask: is this a project file I want to edit, or app data that must survive the container being replaced? The first is a bind mount, the second a named volume.

Common mix-ups

✗"COPY is a kind of volume."COPY bakes files into the image at build time. Mounts attach storage at run time.
✗"Mounting init.sql persists the database."It only provides the setup script. Persist /var/lib/mysql with a named volume.
✗"mysql_data:/var/lib/mysql creates a ./mysql_data folder."No, that's a named volume. Only ./mysql_data:/var/lib/mysql is a bind to a folder.
✗"Two containers can safely share one database volume."They can both mount it, but MySQL expects one server per data directory. Mounting isn't the same as safe concurrent writing.
✗"My data is in a volume, so it's backed up."A volume only outlives the container. It isn't a backup.

Test yourself

You ran docker compose down and your MySQL data is gone. What was missing?

A named volume on /var/lib/mysql. Without it, the data lived in the container's writable layer.

Bind mount or named volume for your Flask source code during development?

Bind mount (./flask:/app), so edits on the host show up immediately.

How do you tell a bind mount from a named volume in -v a:b?

If a looks like a path (./, /, C:\), it's a bind mount. If it's a plain name, it's a named volume.

You changed init.sql, restarted, and the table didn't change. Why?

Init scripts only run on a fresh, empty data directory. The existing volume already has a database. (To start over, deliberately remove the volume.)

Fixes for the repo Added

While turning the notes into this page I spotted a few things in the practice code worth changing. None of them stop the projects from running on Windows today.

  1. Make the Compose paths match the folders. The file is Docker-compose.yml and refers to ./MySQL/init.sql and Flask/., but the folders are mysql and flask. Windows ignores case, so it works there. On Linux (servers, CI, files inside WSL) Compose won't find the file or the folders. Rename the file to compose.yaml and use ./mysql/init.sql and ./flask.

  2. Persist the database. Add a named volume so down doesn't wipe the data:

        volumes:
      - ./mysql/init.sql:/docker-entrypoint-initdb.d/init.sql
      - mysql_data:/var/lib/mysql

volumes:
  mysql_data:

  3. EXPOSE 3307 should be EXPOSE 3306 in 03/mysql/Dockerfile. MySQL listens on 3306 inside the container. Nothing breaks, because EXPOSE is only documentation, but it documents the wrong port.

  4. Delete version: '3.1'. Modern Compose ignores it and prints a warning.

  5. Know what the health check really tests. In the ["CMD", …] exec form no shell runs, so ${MYSQL_ROOT_PASSWORD} is passed as literal text, not the password. The check still passes because mysqladmin ping exits 0 even on "Access denied": the server answered. Use CMD-SHELL if you want the variable expanded.

  6. Keep passwords out of images and code for anything beyond practice. ENV values are visible to anyone with the image (docker image inspect). Pass them at run time instead, and read them with os.environ. See Beyond the notes.

  7. Update the base images. python:3.8-slim and python:3.9-slim are past end of life and no longer get security fixes. Use python:3.13-slim, and switch project 02 to the cache-friendly order.

Beyond the notes

Added A few things the notes didn't reach that show up as soon as you build something real.

CMD vs ENTRYPOINT

ENTRYPOINT fixes the program; CMD supplies default arguments that docker run can replace.

Dockerfile
ENTRYPOINT ["python", "app.py"]
CMD ["--port", "5000"]
You runThe container runs
docker run myimgpython app.py --port 5000
docker run myimg --port 8000python app.py --port 8000

With only CMD (like every project here), anything after the image name replaces the whole command.

Configuration and secrets via environment variables

The projects hard-code demopassword in the Dockerfile, the Compose file and app.py. The usual pattern is to keep values in a .env file that stays out of git, let Compose substitute them, and read them in code.

.env (next to compose.yaml, listed in .gitignore)
MYSQL_ROOT_PASSWORD=change-me
compose.yaml
services:
  mysql_container:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
  flask_container:
    build: ./flask
    environment:
      DB_PASSWORD: ${MYSQL_ROOT_PASSWORD}
app.py
import os
password = os.environ["DB_PASSWORD"]

Same image, different settings per environment, and no secret baked into any layer.

Smaller, safer images

Slim bases (python:3.13-slim) drop tools your app doesn't need. Multi-stage builds go further: install things in a full image, then copy only the result into a slim one. Compilers and build tools never reach the final image.

Dockerfile, multi-stage
# stage 1: install dependencies into a virtual environment
FROM python:3.13 AS build
RUN python -m venv /venv
COPY requirements.txt .
RUN /venv/bin/pip install --no-cache-dir -r requirements.txt

# stage 2: the image you ship
FROM python:3.13-slim
COPY --from=build /venv /venv
WORKDIR /app
COPY . .
USER nobody
CMD ["/venv/bin/python", "app.py"]

USER nobody runs the app as an unprivileged user instead of root. If something breaks out of the app, it has far less to work with.

When something goes wrong

  • docker ps -a: did it exit? The STATUS column shows the exit code.
  • docker logs <name>: the app's own error message is almost always here.
  • docker exec -it <name> sh: look around inside. Are the files where you expected?
  • docker inspect <name>: check networks, mounts, ports and environment.
  • Can't connect? Walk the path: published port, then container port, then 0.0.0.0, then the network and the name.

What to learn next

  • Push an image to Docker Hub: docker login, docker tag, docker push.
  • Build images in CI, for example with GitHub Actions, so every commit produces a tested image.
  • Kubernetes, once you need to run containers across many machines with scaling and self-healing.
  • The official docs: Get started, Compose and multi-stage builds.

Test yourself

With ENTRYPOINT ["python","app.py"] and CMD ["--port","5000"], what does docker run myimg --port 9000 run?

python app.py --port 9000. The arguments replace CMD and are appended to ENTRYPOINT.

Why not put the database password in an ENV line?

It becomes part of the image, readable by anyone who has it. Pass it at run time instead.

What does a multi-stage build leave out of the final image?

Everything from the earlier stages that you don't explicitly COPY --from, such as compilers, build tools and caches.
